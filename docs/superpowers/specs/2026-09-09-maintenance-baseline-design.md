# 第一阶段：本地维护基线验收规格

日期：2026-09-09。依据：维护者已同意先在本地维护，并先建立干净构建与自动启动验证。

本文件固化已讨论的第一阶段范围；详细步骤见 [执行计划](../plans/2026-09-09-maintenance-baseline.md)。长期方向见 [维护路线](../../MAINTENANCE.md)。

## 目标

从一个确定的 Git 提交，在新建的本地源码目录中完成 Windows x64 Release 构建、运行目录整理和最小 X 服务验证，留下能复查的证据。这里的“可复现”指流程与结果可重复，不要求 EXE/DLL 的哈希逐次相同。

## 约束

- 只在本地保存代码、提交和验证记录；不执行 push 或远程发布。
- Windows x64 Release；PowerShell 5.1/7；VS2022/MSVC v143；Python 3.11 或更新版本。
- 不依赖 WSL/Cygwin，不自动下载或安装工具，不自动更新第三方组件。
- 源码路径无空格；工具路径和运行目录路径允许含空格。
- 保留当前工作目录和运行目录；干净构建从已提交源码建立独立本地 worktree。
- 运行验证不关闭访问控制，不修改全局环境、注册表或防火墙，不终止其他 VcXsrv 实例。

## 现状与证据边界

`bc77b1521` 已在当前主机完成分阶段编译、Portable 整理、21 项测试、35 个 PE 文件的依赖扫描，以及一次使用临时认证的 TCP X 根窗口查询。该记录是本阶段输入；新增验证不能直接沿用旧结果作为通过凭据。

仓库携带的预编译文件仍可能被使用。例如 libxml2 运行库由现有文件清单复制。这不妨碍“干净源码目录构建”成立，但报告必须明确它不等于所有依赖从源代码重建。

## 交付物和验收条件

| 编号 | 交付物 | 验收条件 |
| --- | --- | --- |
| B1 | 环境报告 | 构建入口导出实际选中的工具路径、可获取的版本、目标架构/配置、Windows/PowerShell 版本；Python 包版本来自被选中的解释器；不转储完整环境变量 |
| B2 | 运行依赖验证 | 检查运行目录全部 EXE/DLL 为预期架构；导入 DLL 从运行目录或正确位数系统目录解析；Windows API-set 明确作为系统契约处理；遇到扫描失败、缺少导入或错误位数返回失败 |
| B3 | 自动启动验证 | 最小 PATH 下 `vcxsrv -version` 正常退出；临时认证文件下启动服务器；`xwininfo -root` 返回成功且尺寸为正；有限超时；成功/失败都清理本次子进程并保存日志 |
| B4 | 干净构建记录 | 从已提交版本新建目录，记录构建前状态；完整 All 阶段退出 0，产生 Portable 目录；随后现有测试与 B2/B3 通过；原工作区不被清理 |
| B5 | 证据和失败定位 | JSON 结果记录提交、环境、命令参数（隐藏认证内容）、步骤状态、退出码、用时、日志；失败指出步骤；缺少前置条件记为 NOT_RUN 并返回非零，不伪装成功 |

根窗口尺寸不固定为 1920×1080；此前该尺寸只描述当时机器。运行验证不以日志中出现某个品牌 GPU 文本作为通过条件。

## 设计

### 环境采集

在 `buildall.ps1` 增加可选 `-EnvironmentReport` 文件路径。复用已经完成的工具选择和 VS 环境初始化，在进入实际编译或 CheckOnly 返回前导出 UTF-8 JSON。未提供参数时保持现有行为。

报告字段固定为 `schema_version`、`source_commit`、`target`、`host`、`tools`、`python_packages`。`tools` 每项含 `path` 和 `version`，键名为 `python`、`cl`、`msbuild`、`dumpbin`、`flex`、`bison`、`perl`、`nasm`、`gperf`、`jom`、`msvc`、`sdk`；SDK/MSVC 的 path 为目录。没有可靠版本信息时写 `null`，不伪造版本。BuildTool 阶段没有选择的工具不写入报告。SDK/MSVC 从当前初始化环境记录，不能只记录机器上最新安装的版本。

### 运行验证

新增标准库 Python 工具 `tools/verify_runtime.py`。必需参数为 `--runtime`、`--dumpbin`、`--source-commit`、`--output`，可选 `--display`（默认 97）和 `--timeout`（默认 30 秒）。`--source-commit` 是执行者记录的构建源码提交，用于标识产物来源，工具不能单靠它证明二进制来源。输出目录不得与运行目录重合或相互包含，日志放在输出目录。

先验证文件和 PE 导入，再启动。子进程 PATH 仅含运行目录和 Windows System32；移除子进程环境里可能干扰的 `DISPLAY`、`XAUTHORITY`、`XLOCALEDIR`、`XKEYSYMDB`、`XERRORDB`、`XKB_CONFIG_ROOT`，不修改父进程。

使用随机 cookie 和临时 Xauthority，给本次 server 与 client 显式指定；不把 cookie 写进报告。预检显示号对应端口，如已占用则以明确失败结束，用户可以换 `--display`。绑定竞争导致启动失败同样如实报告。

启动参数包含 `-multiwindow -clipboard -listen tcp -auth`；用循环查询代替“睡固定时间后认为成功”。记录版本输出、服务器日志、客户端标准输出/错误。清理范围仅限持有的本次子进程句柄，临时认证文件在进程退出后移除。超时也必须清理。

静态导入扫描不能覆盖所有 `LoadLibrary` 路径，最小启动测试也不能证明全面 OpenGL 兼容；报告保留此限制。

### 干净构建和记录

新 worktree 只包含 Git 跟踪的文件，不复制主目录里的 ignored 产物。先执行构建，再执行依赖 mhmake 的完整脚本测试，避免尚未编译导致测试自动跳过而被误报通过。

本地原始记录放在 `.local-validation/`（加入忽略规则），包括环境 JSON、完整构建日志、测试日志和运行结果。提交简短的 `docs/validation/` 报告，写入实际结果和被验证提交；不把机器完整环境、认证材料、临时目录内容或运行二进制提交到 Git。

## 本阶段不覆盖

Debug/Win32、多台电脑、Linux GUI 全场景、中文输入、剪贴板内容正确性、多显示器、GL 渲染正确性、NSIS 安装包、签名、CMake 迁移和第三方版本升级分别安排，不作为本阶段偷偷扩大的工作范围。

## 失败处理

工具不足时指出缺少项并结束，不安装；构建失败时记录首个有效错误和组件，先定位再修复；需要改 C/C++ 功能或更新依赖时单独说明影响。已有失败记录必须保留，重跑生成新记录，不覆盖为通过。只在 B1–B6 的证据齐全后宣布基线完成。
