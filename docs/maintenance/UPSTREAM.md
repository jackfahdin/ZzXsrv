# 依赖来源与更新规则

生效日期：2026-09-10。按维护者要求，ZzXsrv 不再保留上游源码分支。本文替代此前 upstream/master 两层结构；文件名保留以兼容既有文档链接。

## 主线与来源

- `master` 为唯一长期开发主线，提交历史保持线性。远程为 `git@github.com:jackfahdin/ZzXsrv.git`。
- 按维护者 2026-09-10 的约定，助手可在完成相应验证后自行提交本地改动；所有远程 push 均由维护者操作，助手不主动推送。
- 依赖版本、上游 commit/tag、实际导入来源及证据统一记录于 [依赖来源文档](../dependencies/SOURCES.md)。对应机器可读清单为 [来源清单 JSON](../dependencies/SOURCES.json)。
- 项目从原 VcXsrv 的固定整合提交继承第三方源码。初次继承链接与组件官方来源链接分别记录，不声称曾独立下载每个官方包。
- 原作者记录的同步点、清单声明的版本、源码自报版本及无法证实的来源分别标记。不能凭目录名或版本号补造 tag、提交号或下载记录。

## 后续维护步骤

1. 从当前 master 的固定提交开始，明确需要更新的组件和收益；先核对已应用补丁与本地 Windows 适配。
2. 从官方来源取得固定 commit/tag 或正式源码包，记录精确 URL、修订、下载日期及源码包 SHA-256。发布包的 hash 验证与目录内自报版本是不同证据。
3. 在临时工作目录比较并引入改动，只更新目标组件及必要消费者，保留版权、许可证、本地接口与构建适配。组件来源更新和本地适配分别提交或在提交正文中明确列出。
4. 同步更新依赖来源文档和 JSON，包括路径映射、裁剪、嵌套依赖、补丁与仍然未知的信息。无需建立来源快照分支，也不执行旧 `scripts/legacy/upstream/sync.bat` / `scripts/legacy/upstream/synchronise.py` 的整目录同步流程。
5. 按改动范围完成回归、干净构建、运行验证和实际应用验收。保留固定源码、命令、工具版本、结果与可回退提交；纯历史或文档整理以文件树、来源和链接核对为准。
6. 使用快进、rebase 后快进或 squash 整合，使 master 不出现 merge commit。完成后清理临时分支和工作区登记；有运行产物或日志的目录先保留其数据。助手完成本地提交后交付结果，远程推送由维护者操作；只推送所需主线，不使用 `push --mirror` 或全量旧标签推送。

当前本地已设置 `pull.ff=only` 与 `merge.ff=only`。这些是便利设置，不取代上面的约定；新克隆需要自行设置，不能假定配置会随 Git 提交传播。

## 验证边界

当前主线已包含 GLX、XFIXES、输入处理、RENDER/RECORD 修复与原生构建能力。RENDER/RECORD 已取得本组实际使用确认并完成快进整合，合入后 97 项测试通过，见[本组报告](../validation/2026-09-10-render-record.md)。输入候选已取得维护者实际使用反馈，并按当前目录恢复、完整构建及重新验证后整合；见[整合报告](../validation/2026-09-10-xserver-input-integration.md)。剪贴板/OpenGL 未验证，GUI-001 暂缓排查，不能将有限实际反馈描述为全场景通过。

有程序行为变化时，启用相关本机工具及运行测试，不以跳过代替通过；X Server 等图形相关变动需实际应用场景。All 阶段仍使用继承的 libxml2 预编译文件，其完整来源与重建是独立待办。

旧的分支规则、旧 SHA 与历史测试数字保留在日期明确的验证材料中。其“upstream 分支”“主线合并”和标签描述仅表示当时状态；现行规则以本文和[整理记录](../validation/2026-09-10-repository-reorganization.md)为准。

XKB 后续修复正在独立候选分支验证，范围与来源见 [XKB 报告](../validation/2026-09-10-xkb.md)。候选通过实际使用确认之前，不计为 master 已整合；仍只允许本地提交，由维护者自行 push。
