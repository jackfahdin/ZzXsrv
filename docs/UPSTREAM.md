# 上游更新与组件维护规则

生效日期：2026-09-09。维护者已确认“upstream 依赖源码快照、master 整合开发”的两层结构，替代此前“原作者整合快照”的定义。

## 两条维护主线

`upstream` 保存依赖组件的来源快照，按本项目既有目录布局组织，不加入我们的 Windows 适配、构建修改和功能修复。`master` 保存可开发、可构建的整合版本，包括继承的 VcXsrv 适配和我们的修改。

项目以原作者 VcXsrv 为初始来源，不再维护其整合快照分支，也不以其是否更新决定组件是否更新。今后直接评估 X.Org、Mesa、OpenSSL 等组件来源；需要原作者的某项改动时，在开发分支单独引入并注明出处。

初始 `upstream` 使用本地已有 `released` 的组件集合，完整来源、根目录对象和文件树固定于 [DEPENDENCIES.json](DEPENDENCIES.json)。它沿用历史导入布局、裁剪和辅助文件，不等于所有组件 Git 仓库的完整克隆。`libxml2`、`libregex`、`libwinmain` 等仅见于初始整合树的目录没有被冒充成原始组件快照；它们继续保留在 `master`，取得可验证的来源后再单独建立组件基线。

## 更新优先级

| 类别 | 处理规则 |
| --- | --- |
| 相关安全修复、严重崩溃或数据破坏 | 优先确认受影响组件、版本和实际使用路径，选择有来源的修复提交或稳定版本，不以版本号较旧直接判定受影响 |
| 日常使用故障 | 建立复现步骤和回归验证，优先选择范围小、能解释的修复 |
| 普通组件更新 | 按组件或相互依赖的一组组件分批评估，记录依赖关系、接口变化和收益 |
| 大版本、新功能、构建系统迁移 | 有具体需求与独立计划后实施；避免与一般修复混在同一更新中 |

每次准备维护版本时检查更新；出现相关公告或实际问题时及时评估。未建立无人值守监控，不默认定期执行远程操作。开发主线可以保持稳定快照，不能为了追求最新版本一次性替换全部组件。

首轮 [组件更新评估](validation/2026-09-09-component-update-assessment.md) 是固定于旧源码的历史评估。当前 GLX 已合入，XFIXES 是已完成自动验证的独立候选；后续待办统一见 [计划状态](PLAN_STATUS.md)，候选证据见 [XFIXES 报告](validation/2026-09-09-xfixes-request-length.md)。

## 更新依赖快照并整合

1. 记录当前 `upstream`、`master` 和 `git merge-base upstream master`。保持开发目录干净，在独立工作区准备依赖导入。用 `git merge-base --is-ancestor upstream master` 判断当前依赖快照是否已整合；没有合入时，先核对已有候选，避免重复导入。
2. 从组件官方仓库的固定提交或正式源码包取得本次需要的源码；在取得新远程源码前说明来源和范围。记录来源 URL、完整提交号或版本、源码包 SHA-256，以及目录映射、裁剪和嵌套依赖规则。不得以文件中的版本号代替来源证据。
3. 在当前 `upstream` 的子提交中仅更新目标组件的来源文件，保留无关组件和版权材料。初始导入的辅助脚本仅为历史材料，不在主开发目录执行 `sync.bat` / `synchronise.py`。组件上游的公开补丁可以按顺序导入，但须记录基准和每个来源提交；本地适配始终写在开发分支。
4. 从 `master` 建立 `codex/update-<component>` 工作分支，普通合并新的 `upstream`；依据最近已整合的基线做三方比较，逐项检查删除、改名、生成文件、构建规则及嵌套组件的冲突。在该工作分支更新 `DEPENDENCIES.json`：保留集合初始来源，更新快照提交、文件树和根目录对象，并在 `component_updates` 中追加本次组件的来源、映射和校验记录。
5. 完成对应构建、测试和实际场景验证及独立审查后，再合入 `master`。快照导入不代表构建通过；验收期间 `upstream` 可以领先 `master`。验证记录应同时标明候选开发提交与依赖快照提交。

本次整理的一次性基线合并保持原 `master` 文件树不变，依据是原项目已经整合该 `released` 基线。此做法不能作为日常更新模板：后续禁止用保留开发树的空合并跳过新组件内容，也不再次使用无共同祖先合并。初始合并及不变性证据见 [整理记录](validation/2026-09-09-component-baseline.md)。

## 组件修复与本地适配

来自组件上游的来源更新优先先记录在 `upstream`，我们的适配与功能修复进入 `codex/*` 并最终进入 `master`。同一次维护中，原始来源更新与本地适配使用不同提交，均注明原因和验证证据。

整理前已经进入 `master` 的修复和候选分支中的修改保留原提交，不在本次倒填到依赖基线。以后组件快照包含同一修复时，核对等价改动与冲突，避免重复应用。本次没有合入尚待验收的候选分支，也没有升级组件。

更新共享协议、生成器接口或链接库时，连同消费者一起验证。X Server 产品版本与组件源码版本的关系以来源清单和实际差异判断。

## 本地适配与证据

`master` 保留继承的全部适配。新 `upstream` 的初始文件树来自组件集合，二者的完整差异包含继承的 VcXsrv 适配及我们的开发改动，也可能包含布局和组件更新时间差，不能直接当作可应用的补丁集。

用 `git merge-base upstream master` 找到最近已整合的依赖基线，再比较该基线与 `master`。不能直接覆盖 `master` 中的组件目录，否则会丢失适配。没有加入依赖基线的目录继续按其各自的来源证据维护。

我们的修改从首次导入之后单独提交，来源对照见 [迁移记录](validation/2026-09-09-history-restructure.md)。主要维护点为 `buildall.ps1`、`tools/build_native.py`、`tools/build_xkbdata.py`、原生生成器包装、相关 makefile、`tools/package_portable.py`、`tools/verify_runtime.py` 与测试。每次合并前先执行 `git merge-base upstream master` 取得最近的共同祖先，再以 `git diff --name-status <共同祖先SHA> master` 检查完整本地差异，不能只保留这张文字清单提到的文件。upstream 已前移时，直接比较 upstream 与 master 会混入尚未合入的上游变化，不等于本地补丁清单。

## 更新验收门槛

- 固定更新源码提交，记录实际工具版本；从干净目录完成 x64 Release All 构建。
- 启用本机工具和真实运行集成开关；现有 43 项测试全部执行。以后新增测试按当时总数记录，缺少必需前置条件不能以跳过当作通过。
- 检查运行目录全部 EXE/DLL 的架构和直接/延迟导入；最小 PATH 下完成版本、临时认证、正尺寸根窗口查询和子进程清理。
- 执行更新组件对应的实际场景。Mesa/X Server 改动必须增加实际图形应用验证；键盘、字体、协议和依赖更新分别覆盖受影响功能。最小根窗口查询不替代功能验收。
- 使用 `PASS`、`FAIL`、`NOT_RUN`、`SKIP` 记录状态。必要场景无法验证时不宣称该场景可用；主线整合前解决必需验收失败，并保留独立审查结果。
- 记录源码提交、组件变化、产物清单、回退提交和运行目录；通过后才建立新的本地基线标签。旧标签不移动，旧运行目录不覆盖。

本次依赖基线整理没有程序源码变更，验证以组件集合文件树相等、合并基线关系、开发文件不变、运行文件哈希与文档校验为准；不将其记作重新编译或组件升级。
