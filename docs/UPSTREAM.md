# 上游更新与组件维护规则

生效日期：2026-09-09。依据维护者确认的“旧历史归档、upstream 快照、master 开发”方案。本次建立规则和来源清单，没有升级任何第三方组件，也没有配置自动更新任务。

## 两层上游

第一层为 [原作者 VcXsrv](https://github.com/marchaesen/vcxsrv)：优先评估其已经整合的 Windows 修复与组件更新。第二层为 X.Org、Mesa、OpenSSL 等组件：当原作者尚未处理而本项目确有需要时，单独引入相关修复或升级。

`upstream` 只保存原作者 VcXsrv 的完整快照。从组件上游直接引入的补丁属于我们的维护改动，进入独立工作分支并最终进入 `master`，不伪装成原作者快照。将来原作者包含同一修复时，核对后消除重复适配。

## 更新优先级

| 类别 | 处理规则 |
| --- | --- |
| 相关安全修复、严重崩溃或数据破坏 | 优先确认受影响组件、版本和实际使用路径，选择有来源的修复提交或稳定版本，不以版本号较旧直接判定受影响 |
| 日常使用故障 | 建立复现步骤和回归验证，优先选择范围小、能解释的修复 |
| 普通组件更新 | 按组件或相互依赖的一组组件分批评估，记录依赖关系、接口变化和收益 |
| 大版本、新功能、构建系统迁移 | 有具体需求与独立计划后实施；避免与一般修复混在同一更新中 |

每次准备维护版本时检查更新；出现相关公告或实际问题时及时评估。未建立无人值守监控，不默认定期执行远程操作。开发主线可以保持稳定快照，不能为了追求最新版本一次性替换全部组件。

2026-09-09 已完成首轮 [组件更新必要性评估](validation/2026-09-09-component-update-assessment.md)：先核对 X Server 安全补丁，再分批处理字体、XML 和 OpenSSL；尚未应用任何更新。

## 导入原作者快照

1. 确认工作区干净，保存当前 `upstream` 与 `master` 提交号，选择原作者的明确完整 SHA，并记录来源 URL、日期、发布说明和选择理由。首次导入信息见 [FORK.md](../FORK.md)。
2. 在独立检出中取得该快照，核对完整文件树及许可证材料。当前只在本地工作；取得新远程源码前说明需要的来源和范围，不自动下载依赖或执行同步脚本。
3. 在 `upstream` 的现有历史上追加一个导入提交，提交文件树等于选定的原作者快照。记录旧/新来源 SHA。不要每次重新建立无父根，也不要把原作者的长历史直接合入这条压缩主线。
4. 从 `master` 建立 `codex/update-<topic>` 工作分支，合并 `upstream`。三方合并的共同祖先为最近已经合入 master 的 upstream 快照；尚未完成验收的导入可能使 upstream 领先多个快照。检查删除、改名、生成文件和构建规则冲突，逐项保留或替换本地修改。
5. 完成下面的验收门槛和独立审查后，将更新工作分支合入 `master`，记录来源、取舍、测试结果、失败/未验证场景及回退点。

导入提交只是来源存档，不代表已通过 Windows 构建。即使导入成功，开发主线也必须等待验证。初次历史已压缩，不能直接将原作者 `master` 合入我们的 `master`；否则会重新带入旧历史或产生无共同祖先的问题。

旧 `sync.bat` / `synchronise.py` 是作者历史工具，含有目录假设和删除目的目录文件的选项。它们不作为我们的默认更新入口，不在当前开发目录直接运行。

## 直接更新组件

在 `codex/update-<component>` 中记录原始组件版本或 SHA、目标版本或 SHA、官方来源、相关问题/公告、本地补丁及关联依赖。先建立必要的失败复现，再引入修复。属于本地修改的提交与原始组件更新分开，提交标题与正文均中文，同时保留原补丁作者和来源。

不能仅按整个产品的 21.1.16.1 判断组件版本。Git 快照可能包含开发版本或后续适配；以组件来源记录、源码版本文件和实际差异共同判断。升级共享协议、生成器接口或链接库时，连同消费者一起验证。

## 本地适配与证据

首次导入的文件树保留作者所有适配。需要研究作者对原始组件的修改时，可在历史归档中比较 `origin/released` 和对应原作者 `master`；这只是整合差异，可能包含组件更新时间差，不是可直接应用的纯补丁集。

我们的修改从首次导入之后单独提交，来源对照见 [迁移记录](validation/2026-09-09-history-restructure.md)。主要维护点为 `buildall.ps1`、`tools/build_native.py`、`tools/build_xkbdata.py`、原生生成器包装、相关 makefile、`tools/package_portable.py`、`tools/verify_runtime.py` 与测试。每次合并前先执行 `git merge-base upstream master` 取得最近的共同祖先，再以 `git diff --name-status <共同祖先SHA> master` 检查完整本地差异，不能只保留这张文字清单提到的文件。upstream 已前移时，直接比较 upstream 与 master 会混入尚未合入的上游变化，不等于本地补丁清单。

## 更新验收门槛

- 固定更新源码提交，记录实际工具版本；从干净目录完成 x64 Release All 构建。
- 启用本机工具和真实运行集成开关；现有 43 项测试全部执行。以后新增测试按当时总数记录，缺少必需前置条件不能以跳过当作通过。
- 检查运行目录全部 EXE/DLL 的架构和直接/延迟导入；最小 PATH 下完成版本、临时认证、正尺寸根窗口查询和子进程清理。
- 执行更新组件对应的实际场景。Mesa/X Server 改动必须增加实际图形应用验证；键盘、字体、协议和依赖更新分别覆盖受影响功能。最小根窗口查询不替代功能验收。
- 使用 `PASS`、`FAIL`、`NOT_RUN`、`SKIP` 记录状态。必要场景无法验证时不宣称该场景可用；主线整合前解决必需验收失败，并保留独立审查结果。
- 记录源码提交、组件变化、产物清单、回退提交和运行目录；通过后才建立新的本地基线标签。旧标签不移动，旧运行目录不覆盖。

本次历史重组没有源码变更，验证以文件树相等、归档恢复、文档校验和新提交来源报告为准，不将历史重组冒称为重新编译或组件升级。
