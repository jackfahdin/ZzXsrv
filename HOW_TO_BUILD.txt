Native Windows build (PowerShell, no WSL or Cygwin)
=================================================

Prerequisites:
- Visual Studio 2022 with the Desktop development with C++ workload, v143
  x86/x64 tools, and a Windows SDK.
- Windows Python 3.11 or newer with lxml, mako and PyYAML in that interpreter.
- Strawberry Perl, NASM, WinFlexBison, and a native Windows gperf.
- Optional: JOM for parallel OpenSSL builds. NMake is used when JOM is absent.

The script never downloads or installs tools. It finds VS2022 with vswhere and
looks for generators on PATH. It also checks common Tools/SoftWare directories
on local drives for WinFlexBison and Qt's gperf/JOM. Cygwin/MSYS executables are
rejected. File filtering and font compression use Python instead of Unix tools.
Core keyboard data is generated with the repository's Python/Perl generators;
no Meson is needed. Gettext translation catalogs are not included in this step.

From PowerShell in the repository root:

    .\buildall.ps1 -CheckOnly
    .\buildall.ps1 -Configuration Release -Architecture x64 -Jobs 8

If script execution is restricted, a one-process invocation is sufficient:

    powershell -NoProfile -ExecutionPolicy Bypass -File .\buildall.ps1 -CheckOnly

Explicit tool paths take precedence and an invalid override fails immediately:

    .\buildall.ps1 -CheckOnly `
        -PythonPath D:\SoftWare\Python3\python.exe `
        -WinFlexBisonPath D:\SoftWare\win_flex_bison-2.5.25 `
        -GperfPath D:\SoftWare\Qt\5.15.2\Src\gnuwin32\bin\gperf.exe

Other overrides: -VisualStudioPath (VS installation directory), -PerlPath,
-NasmPath and -JomPath (executable paths). Quote paths containing spaces.
Keep the source checkout in a path without spaces: the existing mhmake include
and library lists still assume this. All environment changes are temporary.

Stages:
    -Stage All           Build everything and assemble the portable runtime.
    -Stage Dependencies  Build FreeType, OpenSSL, pthreads and mhmake.
    -Stage BuildTool     Build only mhmake (always Release).
    -Stage Server        Reuse dependencies/mhmake, build and assemble runtime.
    -Stage Portable      Assemble runtime from existing outputs; no compilation.

The default is All, x64, Release. Debug and Win32 are also selectable; rebuild
dependencies for the selected configuration before using -Stage Server.
Run dist\x64\Release\xlaunch.exe for the startup wizard, or vcxsrv.exe in that
same directory to start the server directly. Keep the whole folder together:
it includes runtime DLLs, fonts, locale and keyboard data. The raw build output
xorg-server\obj64\servrelease\vcxsrv.exe does not have its runtime DLLs beside
it and cannot be launched on its own.

To assemble the runtime again without recompiling:
    .\buildall.ps1 -Stage Portable

Runtime assembly reads the existing NSIS file list and copies local build
outputs plus the matching Visual Studio CRT DLLs. It does not install anything,
write registry entries or require NSIS. Installer packaging remains separate.
The existing NSIS/packageall.sh route remains separate and requires NSIS.

Validated on Windows with VS2022/MSVC 14.44, SDK 10.0.26100.0, Python 3.14,
and WinFlexBison 2.5.25: x64 Release dependencies, mhmake, server, Mesa,
utilities, fonts and core keyboard data build successfully. Windows PowerShell
5.1 and PowerShell 7 preflight checks pass. The portable x64 Release server
starts with a system-only PATH, initializes native WGL and accepts an
authenticated local TCP connection from xwininfo (-root reports 1920x1080).
All 35 packaged PE files have their imported DLLs available locally or in
Windows. Debug/Win32 builds, installer packaging and broader application/GL
compatibility have not been verified.

Build-script tests (standard library unittest; no additional test framework):
    python -B -m unittest discover -s tools/tests -v
Set VCXSRV_TEST_LOCAL_TOOLS=1 to include checks against an installed toolchain.

Local build and runtime evidence (Windows x64 Release)
---------------------------------------------------
Export the selected native tools and Python package versions during preflight:

    .\buildall.ps1 -CheckOnly -EnvironmentReport .local-validation\environment.json

Use the same option on an actual build to record the tools used by that build.
The report contains selected paths and available versions, not the full process
environment. Keep the source checkout path free of spaces; tool paths and the
portable runtime directory may contain spaces.

Verify an assembled runtime with 64-bit Windows Python 3.11 or newer:

    $environment = Get-Content .local-validation\environment.json -Raw | ConvertFrom-Json
    $builtCommit = (git rev-parse HEAD).Trim()
    python -B tools/verify_runtime.py --runtime dist/x64/Release `
        --dumpbin $environment.tools.dumpbin.path --source-commit $builtCommit `
        --output .local-validation/runtime-001 --display 97 --timeout 30

Supply the full commit used to build those binaries; the verifier cannot infer
or prove their source provenance. Use a fresh output directory for every run,
outside the runtime (neither directory may contain the other). Existing evidence
is never overwritten. The output contains result.json, dependencies.json and
separate dumpbin, version, authentication, server and client logs. A rejected
output path cannot receive a JSON report; the CLI explains that error on stderr.

The verifier checks all packaged EXE/DLL Machine fields and direct/delay imports,
including Mesa's import from vcxsrv.exe. Imports must resolve in the runtime root
or native System32; API-set names are recorded as Windows system contracts. It
then checks the server version and runs an authenticated TCP root-window query.
PASS requires positive root dimensions; server process liveness is insufficient.
The subprocess PATH contains only the runtime and System32. Temporary random
Xauthority credentials are redacted from logs and removed after owned children
exit. Global environment, registry and firewall settings are not changed.

Display 97 uses TCP port 6097; choose another --display if occupied. The tool
does not stop other X servers. --timeout bounds each dependency/version/auth
command and the startup/query loop; cleanup has its own bounded process waits.
Exit 0 means PASS. Missing prerequisites produce NOT_RUN and a nonzero exit;
dependency, startup, connection or cleanup failures produce FAIL and nonzero.

To include real desktop integration in the runtime tests, set the following in
a separate PowerShell process (the three parameters are mandatory when enabled):

    $environment = Get-Content .local-validation\environment.json -Raw | ConvertFrom-Json
    $builtCommit = (git rev-parse HEAD).Trim() # Use the actual build's commit.
    $env:VCXSRV_TEST_RUNTIME = '1'
    $env:VCXSRV_RUNTIME_DIR = (Resolve-Path dist/x64/Release).Path
    $env:VCXSRV_DUMPBIN = $environment.tools.dumpbin.path
    $env:VCXSRV_SOURCE_COMMIT = $builtCommit
    python -B -m unittest discover -s tools/tests -p test_verify_runtime.py -v

Integration covers the original runtime, a temporary copy missing libX11.dll,
and a restored copy whose path contains spaces. It runs sequentially and removes
only its own temporary copies. Default unit tests do not launch desktop apps.
Static imports cannot cover every LoadLibrary path, and a root query does not
verify full GUI/OpenGL, clipboard, input-method or multi-monitor behavior.
The clean-build baseline and precise validated source are recorded separately
under docs/validation; see docs/validation/README.md for evidence conventions.

Legacy WSL/Docker build instructions
====================================
The following instructions describe the older shell entry point, which retains
machine-specific paths and may require adjustment. Use buildall.ps1 above for
native Windows builds.

Prerequisites:
- Visual Studio 2022 Community Edition
- Strawberry perl portable edition installed in c:\perl
- Cygwin (with the following packages: bison, flex, gawk, gperf, gzip, nasm, sed, python27, python38, python38-lxml)
- Python39 with lxml and mako
- To build the installer: nsis

or make it easy on yourself and use the new Docker-based build environment:

Run buildDocker.cmd and give it a couple hours to build the build environment.
From inside the VcXSrv source directory, launch the build environment using

		runDocker.cmd

When the container is up, run the following to clone the source into the container and enter the Cygwin build environment:

		git clone src vcx
		cygwin
		cd /cygdrive/c/vcx
        export SHELLOPTS
        set -o igncr

Now you can build a 64-bit Debug build on an 8-core system...

		./buildall.cmd 1 9 D

buildall.sh <32/64-bit flag> <build tasks> <Debug/Release flag> [Build deps flag]

Where:
  - 32/64-bit flag - 1=64-bit, 0=32-bit
  - build tasks is the number of parallel build tasks to run (use cpu count + 1)
  - Debug/Release flag - D=Debug, R=Release, A=All
  - optional Build deps flag - N=Only build the server
